# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A first-person, grid-based dungeon crawler in the style of Eye of the Beholder, in Godot 4.7 (Forward Plus, GDScript). Python (Pillow) generates all pixel art. Development is on Windows; use Git Bash or PowerShell.

## Display and pixel sizes (read this before touching any UI or art)

- **Base resolution is 640x360** (`project.godot`: `stretch/mode = viewport`, `scale_mode = integer`, default canvas texture filter nearest, window override 1280x720). The window scales it by whole numbers only (1280x720, 1920x1080, 2560x1440; a window that isn't an exact multiple gets even letterbox bars), so pixels are never blurred or uneven.
- **The dungeon view is a `SubViewport` rendered at the size it is shown, 416x260 (1:1, `VIEW_SCALE` 1)**, in the top-left (`ui_layout.gd`: `VIEW_SOURCE`, `VIEW_SCALE`, `VIEW`, 416x260 at 8,8), with nearest filtering. It used to be rendered at 208x130 and enlarged 2x (chunky 2x2 pixels); it was doubled so monsters and textures can carry twice the detail. A skeleton standing one tile ahead is about **150 screen pixels tall** (the 64-art-pixel frame was 76 view px; now the 128-px frame is 152). The dungeon, player and camera live inside it (`View/GameView/Port`, found with `%Player` / `%Dungeon`, or by group); everything else is drawn at the full 640x360 on `CanvasLayer`s above it. The main menu's backdrop is rendered the same way (640x360, 1x).
- **UI art is drawn at 2x**: each logical art pixel is a 2x2 block (the dungeon view is no longer the same pixel size: it is finer). The generators draw on the small logical grid and enlarge it by `scale` (`artio.save_png(..., scale=2)`; `python tools/art/build_all.py --scale 2`, the default; generators whose `build()` takes `scale`: frame, ui, portraits, items). **3D art has its own scale, `--world-scale` (default 2, `artio.world_scale()`, env `ART_WORLD_SCALE`)**: the wall/floor/ceiling/door/plate/stairs tiles are 128x128 and the monster frames 96x128 (skeleton, guard) / 96x96 (slime, acid slime), enlarged nearest-neighbour from the procedural grid, and **monster `pixel_size` is halved in the `.tres` files (skeleton 0.014, slime 0.02) so they keep their world size**; if you change the world scale, change those too. The variant monsters are made by hand: `gen_skeleton.py --seed 7 --bone ash --weapon axe --helmet --name skeleton_guard` and `gen_slime.py --seed 5 --colour acid --contents skull --name slime_acid` (`build_all` does not run them). The item floor sprites (48x48), torch, lever and key sprites are NOT doubled. Place UI at **even pixel coordinates** so its 2x2 blocks line up with the frame's. Text is Press Start 2P at 8 or 16 (a project-wide default font, `gui/theme/custom_font`).
- **Display modes** (`display_manager.gd`, the `DisplayManager` autoload in `project.godot`; `Settings.fullscreen`, saved under `[display]` in `user://settings.cfg`): the game starts in **borderless fullscreen** (`Window.MODE_FULLSCREEN`, not exclusive) unless the saved choice is windowed. Alt+Enter toggles at any time (the autoload runs while paused), as does the Options button, which listens to `mode_changed`. Windowed opens at the largest whole multiple of 640x360 that fits the screen's usable area including the title bar (`DisplayManager.best_scale(usable, extra)`, measured after a frame because the decorations only exist then), centred. Leftover screen is black bars in both modes (integer scale; the engine's own transform maps clicks, bars included, so no input code was needed). Nothing happens under `--headless`. In a `-s` SceneTree test, autoloads join the tree *after* `_init`, so `await process_frame` before using `root.get_node("DisplayManager")`; tests of display switching must set `Settings.path` to a temp file first, and run windowed (not headless).
- Mouse positions are in the 640x360 space everywhere. The 3D view's clicks come from the `SubViewportContainer`'s `gui_input` (`game_view.gd`, which calls `Player.world_click`), not from input forwarded into the SubViewport, so they too are screen coordinates (tested pixel by pixel at the view's corners and edges, with and without black bars). Clicks pick up or put down the item on the tile in front wherever they land in the view; monsters are not clickable (heroes attack through their hand buttons).

## Design references

It covers stats, hit chance and damage formulas, cooldowns, party slots and melee, monster targeting, data structures, the script list, starting numbers, and the agreed decisions (swinging at air uses the cooldown; the back row steps up; adjacent monsters stop moving).

## Testing

Nothing is checked in for the game itself. The working approach has been throwaway headless scripts that `extends SceneTree`, instantiate `res://scenes/main.tscn`, teleport the player (`p.cell = ...; p.position = ...; p._report_position()`), call `p._try_move(...)` / `p._interact()` / `monster._on_tick()` directly, `await create_timer(...)`, and print PASS/FAIL. Gotchas:
- A SceneTree script must call `quit()` on every path; a runtime error before it leaves Godot running forever. Wrap the run in `timeout 120`.
- Godot auto-names code-created nodes (`@Timer@2`), so find them by type, not `get_node("Timer")`.
- Input is polled (`Input.is_physical_key_pressed`), so tests call methods instead of simulating keys.

## Architecture

**Level data is a script, not a scene.** `scripts/dungeon_map.gd` holds `MAP` (0 floor, 1 wall, 2 door, 3 locked door, 4 stairs, 5 portcullis, 6 cracked wall), start tile, and lists for `TORCHES`, `KEYS`, `MONSTERS`, `DOOR_IDS`, `PLATES`, `LEVERS`. It also holds *run state* as `static var`s (open doors, keys held, occupied tiles, `player_cell`). `reset_run()` is called from `dungeon_builder.gd::_ready`, which is what makes `reload_current_scene()` a full restart. Edit levels there; everything else reads from it.

**The level** is traced from a hand-drawn map (`map.png`, a 23x23 grid; the data is shifted one column right and two rows down, 22x25 with a wall border and two closets north of room 7, and its comments use the map's room numbers). Translation rules: an archway is open floor, a portcullis is a door in `DOOR_IDS` driven by levers/plates (`gate_n`: two levers, one on each side; `gate_s`: a plate in room 6 and a lever on the stairs-corridor side), and the up stairs are the landing the player starts on (4,9) facing east. **Two stairs tiles** (a pair at the end of the south-east corridor, behind locked door 2; each completes the level). The map's top-left down stairs were deliberately removed (too close to the start) and that corridor is a dead end. Two locked doors (the corridor to the stairs, and a loot closet north of room 7) and three keys (room 5, room 7, room 4); one key is enough to finish. 15 monsters of four kinds (`skeleton`, `skeleton_guard`, `slime`, `slime_acid`; the last two are generated with `gen_skeleton.py`/`gen_slime.py` and have `.tres` files like the originals). Several items may share a closet tile (they stack as a pile). A throwaway BFS walk-through (doors, keys, levers, plate, both exits) was used to check it is completable; redo that whenever the map changes.

**`DungeonMap` is `preload`ed, not a `class_name`.** Each script does `const DungeonMap := preload("res://scripts/dungeon_map.gd")`. A `class_name` isn't registered until the editor scans, so headless runs and fresh files fail with "Identifier not declared". Follow this for new shared scripts (`MonsterDef` is likewise referenced untyped).

**Scene tree** (`scenes/main.tscn`): `Dungeon` (builder; creates all meshes/sprites/lights in code), `Player` (with `Camera3D` and a torch light), `Party`, plus self-contained overlays `DebugOverlay` (Tab: a small translucent 11x9-cell minimap that follows the player, top-right of the 3D view, plus `x,z facing`; `minimap.gd`), `Hud`, `PartyHud`, `LevelComplete`, `GameOver`.

**Other top-level scenes:** `scenes/main_menu.tscn` is the **startup scene** (`run/main_scene`; F5 in the editor opens the menu, press New Game or run `main.tscn` directly with F6) and is also reached from Game over's "Quit to Menu" via `get_tree().change_scene_to_file()`, not as a child of `main.tscn`. It is a `Node3D`: its background is the game's own level -- the same `dungeon_builder.gd` with `populate = false` (architecture, torches and lever only, no items or monsters), the same textures, a camera at cell (6,13) looking east down the long corridor (`VIEW_CELL` in `main_menu.gd`: update it if the level changes) with a flickering camera torch and a slow drift, rendered in a 640x360 viewport at 1x -- with the UI on a `CanvasLayer` over it. Buttons: New Game, Load Game (greyed out without a save; `SaveGame.load_game`), Options, Quit. **Options** has three volume rows, Master / Music / Effects (see **Audio**), each 0-100% in 10% steps via -/+ buttons or the left/right arrows on the focused row, a `SCREEN: FULLSCREEN / WINDOWED` button (see **Display modes**) and a `FOG: ON / OFF` button (see **Spell lighting**); all saved to `user://settings.cfg`; a change plays a click so it can be heard. The menu applies the saved volume at startup, so launching `main.tscn` directly runs at full volume. The font is **Press Start 2P** (SIL OFL, `art/fonts/`, licence in `OFL.txt`; keep it with the font): use sizes that are multiples of 8 (title 16, text 8) and keep its `.import` settings `antialiasing=0`, `hinting=0`, `subpixel_positioning=0` or the pixels blur. The title's drop shadow is `rust_700` at 2,2 with a 2px `ink` outline; every UI colour is a palette colour (hard-coded as palette-named consts in `main_menu.gd`, as in the HUD).

**Decoupling is by node groups.** The player never holds references to the world; it calls `get_tree().call_group(...)`:
- `"dungeon"` (builder): `open_door`, `pull_lever`, `refresh` via `call_group`; `item_at`/`take_item`/`place_item` need a return value, so callers fetch the node directly instead (`get_tree().get_first_node_in_group("dungeon")`)
- `"hud"`: `show_message`
- `"level_complete"` / `"game_over"`: `show_screen`
- `"party"`: `act(slot, hand)`, `cast(slot, hand, spell, target)`, `attack(slot)`, `take_hit_from(monster)`

So the overlay, HUD and level-complete scenes can be deleted from `main.tscn` without breaking anything. Keep new UI the same way.

**Screen layout** (`ui_layout.gd`, the one place the rectangles live): the classic Eye of the Beholder arrangement on the 640x360 screen -- the 3D view top-left (`VIEW`, 416x260 at 8,8, a 416x260 SubViewport at 1x), the party at the right (`PARTY`, 2x2 panels of 98x170), the message log (`LOG`, 296x76, about four lines) and the movement arrows (`ARROWS`) along the bottom -- inside a stone frame. **`tools/art/gen_frame.py` draws `art/ui/frame.png` from the same rectangles (kept there in logical pixels, half of these: change both) and the 3D view window is the only transparent part of it**; a test checks the hole is exactly `VIEW`. The frame (`ui_frame.gd`, canvas layer 4) sits over the SubViewport's layer (1); the HUD layers are log 5, arrows and party 6, then debug overlay, inventory, cursor, end screens. World clicks (item pickup) come from `GameView`'s `gui_input` and call `Player.world_click`, so the frame and panels never pick things up. **Movement arrows** (`move_arrows.gd`, six 32x32 buttons from `gen_frame.py`) call `Player.command(kind)`, the same path the W/A/S/D/Q/E keys use; they act on `button_down` (a quick tap can't fall between frames) and repeat while held; the player ignores a command while a step is animating. **The message log** (`hud.gd`) is a history, newest line brightest, trimmed to 40 lines; `show_message(text)` appends, `show_message(text, true)` and `clear_message(only_if)` use the one-line status row under the log (item name on hover, "Heal whom?"); `Hud.last_message`/`last_tone`/`lines` are what to read in tests, `message` is only the status row. **Party panels** (`party_hud.gd`): 64x64 portraits (the art's own size), two 28x28 quick slots under them, 32x32 hand buttons (`hand_sword_small.png`), bars 6/4/4 px; content margins are 6/4/4/4 so every element lands on an even pixel; the portrait is centred by anchors, so shake tweens must return to its remembered `rest_x`, not 0. **Item icons come in three sizes**: `icon` (48x48, inventory and cursor), `hud_icon` (24x24, hand and quick slots, `ItemDef.hud_texture()`), `floor_icon` (48x48 -- the same drawing as `icon` -- the 3D sprite, not enlarged; `icon_pixel_size` is 0.01 so it keeps the world size the old 12x12 version had (key: 32x32, 0.015)). Don't trust a `resized` signal for the first layout of an anchored child (the buff ring missed it): anchor children to fill instead. Overlays (inventory, character sheet, spell menu, end screens, main menu) are laid out natively at 640x360 with 2x-sized constants; a `CanvasLayer` `scale` was tried and rejected (full-rect Controls keep the full 640x360 size under it).

**Grid movement** (`player.gd`): input is polled in `_process`; a step or turn is a 0.2 s tween and input is ignored while it runs. Logical position (`cell`, `facing`) changes at the *start* of a move, and `_report_position()` publishes it via `DungeonMap.player_cell` plus a `refresh` call. F is edge-triggered (a held key must not repeat a lever pull). Facing indices: 0 N, 1 W, 2 S, 3 E (increasing = turning left).

**Cracked (destructible) walls** (MAP tile 6; `DungeonMap.is_destructible(cell)`, run state `broken_walls`, which `reset_run` clears): `is_wall` stays true until the cell is in `broken_walls`, so movement, sight, monsters and missiles all just work. The tell is `art/tiles/wall_cracked.png` (`gen_tiles.py`): a jagged crack with a glowing torch-coloured core, drawn **once in each of the six cells of a 3x2 grid** because Godot's `BoxMesh` shows each face as one 3x2-grid cell of the texture (a single long crack fell between faces and was invisible; a dark-only crack vanishes in the dim light). Only tile 6 can break; walls, doors and portcullises refuse (`Dungeon.break_wall` returns false). **Breaking**: the **War Hammer** (`data/items/war_hammer.tres`, `ItemDef.breaks_walls`; 5-12 damage, -1 attack; lies in room 3) breaks it with one swing at the wall in front (`Party._swing_at_wall`, front row only; any other weapon or fists say it holds), and **Fireball** (`SpellDef.breaks_walls`) can be cast at a cracked wall that is the first thing in the path (otherwise still "nothing to target") and its blast also breaks cracked walls within 1 tile of a monster it hits. `Dungeon.break_wall(cell, burst, delay)` sets the state at once (`delay` only holds back the show so a fireball arrives first); `restore_broken_walls` (save/load, `broken_walls` list in the save, old saves without it load) breaks silently. The show (`_show_break`): the wall block goes, the cell gets a floor and ceiling, **static rubble** (`rubble[cell]`: 8 small blocks in the wall's own material, seeded by the cell so it looks the same after loading) stays forever, and `wall_debris.gd` bursts **16 `RigidBody3D` cubes** (wall material, bounce 0.35) with a dust puff, the `rumble` sound placeholder and a small screen shake. The debris node carries temporary colliders (floor, ceiling, the walls around) and removes itself, cubes and all, once everything has been still for 0.5 s or after 4 s, so no physics bodies remain. The level has one: a cracked wall at (2,6) at the dead end of the west corridor, hiding a closet of loot.

**Portcullis** (MAP tile 5, `DungeonMap.is_portcullis`; also counts as a door in `is_door`, so doors, saves and `open_doors` treat it the same): an iron grate you can see through. `tools/art/gen_tiles.py` draws `art/tiles/portcullis.png` as transparent bars (about half the pixels clear); `dungeon_builder.gd` shows it as one double-sided `QuadMesh` with an alpha-scissor material (`_make_grate_material`), not a box. It blocks movement and missiles while shut but **not sight** (`has_line_of_sight` skips it, so monsters see you through it), can never be opened by hand (F or `Dungeon.open_door` refuse; the player answers "The portcullis won't budge." to F or to a left click on it, only while it is shut), and is raised only by its `DOOR_IDS` lever or plate. It rises and drops with `PORTCULLIS_TIME` 1.5 s (doors: 0.6 s) and plays the placeholder `portcullis` rattle (`gen_sounds.py`) instead of the door creak. The two gates of the level are portcullises. In tests, wait about 1.8 s after a switch, not 0.9.

**Doors, plates, levers** (all in `dungeon_builder.gd`): `_drive_door(cell, open)` is the single path that opens or closes any door. A door is only walkable once its slide finishes (`DungeonMap.open_doors`), closing blocks immediately, and a door never closes while the player or a monster stands in it. Doors with an ID in `DOOR_IDS` ignore F and are driven only by their plates/levers via `refresh()`; a door is open if *any* of its switches is active.

**Items** (`item_def.gd` resource in `data/items/*.tres`, listed by cell in `DungeonMap.ITEMS`): `dungeon_builder.gd` owns both the floor sprites and the run-time state (`item_at`/`take_item`/`place_item`), unlike monsters/doors there's no DungeonMap-level tracking. Left click picks up the item on the tile in front onto the cursor overlay (`cursor_item.gd`, group `"cursor"`, fetched directly like `"dungeon"`) or drops the held one there; the cursor is the party's single "hand" (one item), shared with the inventory screen. A locked door uses up a key from the cursor first, otherwise from any party member's backpack (`player._take_key` -> `Party.take_key`, dead members' packs included so a key can't be stranded on a corpse); it used to check only the cursor, which broke as soon as keys could be stored in the inventory. **What items do** (all in `party.gd`, no UI needed to test): an equipped **weapon** (first WEAPON in a hand slot, left first; a backpack weapon doesn't count) adds its `attack_bonus` and *replaces* the holder's bare-handed damage range in `effective_stats()`, which `attack()` uses -- never mutate the shared `CharacterDef`. `use_item(slot, def)` (right-click in the inventory) returns `{used, message, close}`: a **potion** (`heal_amount`) heals the member whose inventory it's in, capped at max HP, refused at full health or if dead; a **scroll** (`spell_damage_min/max`) hits the first monster in the straight line ahead (up to `MISSILE_RANGE` 4, stopped by walls and closed doors), never misses, is consumed, and closes the inventory so the result is visible. `defence_bonus` (armour) is still data only. Items have two icons: `icon` (24x24, slots and cursor) and `floor_icon` (48x48, the floor sprite; falls back to `icon`). Icons come from `tools/art/gen_items.py`. Pickup/drop isn't gated on the click actually landing on the sprite, only on the item being on the front tile -- deliberate, for headless-testability.

**Inventory** (`inventory_screen.gd` + `inventory_slot.gd`/`inventory_floor_drop.gd`, group `"inventory"`, opened by clicking a portrait on `party_hud.gd` or inside the screen itself): shows one "focused" `Party.Member`'s two hand slots, armour slot and 12-slot backpack (new `Member` fields: `hands`, `armour`, `backpack`, pure data -- nothing in combat reads them yet), plus a strip of every member's portrait. **One input system, Eye of the Beholder click-to-click, no drag and drop:** the cursor is the hand; click a slot to pick up, click a slot to put down (swap if occupied, refuse with a status-line message if the type doesn't fit), click a portrait to put the held item in that member's backpack or, empty-handed, to switch to them, click outside the window to drop it on the floor in front. Handlers act on the mouse **press**: Godot routes the release to whichever control received the press, wherever the pointer ends up, so a release-based handler can't tell where the player let go (this was the "item lands in the wrong slot" bug, along with an earlier drag-and-drop system competing with the cursor). Item slots are 24x24 and draw their icon at native size, centred; portrait slots are 16x16 and scale the 32x32 portrait to exactly half. **A `TextureRect` needs `expand_mode = EXPAND_IGNORE_SIZE` to be smaller than its texture** -- without it the strip portraits drew 32x32 over their neighbours while the hit boxes stayed 16x16. The window must stay inside the 640x360 screen (check with a layout probe after changing slot sizes). Right-click on a consumable uses it (see Items). The screen pauses the game (`PROCESS_MODE_ALWAYS`); `CursorItem` must also be `PROCESS_MODE_ALWAYS` and on a canvas layer above the inventory (15 vs 11), or the held icon freezes / draws behind the window. The window panel stays mouse-filter Stop so a click between slots does nothing instead of dropping the item on the floor. **Test GUI input through real routing** (`root.push_input(event, true)` with viewport-space positions), not by calling `_gui_input` directly -- direct calls skip routing and passed while the real game was broken.

**Monsters** (`monster.gd` + `MonsterDef` resource in `data/monsters/*.tres`): new monsters are data plus a line in `MONSTERS`. A monster claims its destination tile in `DungeonMap.occupied` when a step starts and frees the old one when it ends. AI is a staggered timer: chase if within sight range (grid distance) with `has_line_of_sight`, else wander; orthogonal moves only. Next to the party a monster stops moving and attacks on its own `attack_interval` timer.

**Stacks** (`item_stack.gd`, `stack_count.gd`): every place an item can sit -- hand, armour, backpack cell, quick slot, the cursor, a floor tile (one of the stacks in `dungeon_builder.items[cell].pile`) -- holds an `ItemStack` (`def` + `count`) or null, never a bare `ItemDef`. `ItemDef.max_stack` (default 1 = never stacks; Healing Potion 9; scrolls stay 1) decides what merges. `ItemStack.wrap()` turns an `ItemDef` into a stack of one, so `cursor.hold(def)`, `set_quick`, `place_item` accept either. Never share one stack object between two places; `take_one()` makes a new one. Rules: picking up (slot, world) takes the whole stack; clicking a held stack onto a matching backpack/quick stack merges up to `max_stack` and the remainder stays on the cursor; right-click on a stack of 2+ splits one onto the cursor (or adds one to a matching stack already held), a single item is picked up (quick slot) or used (inventory backpack); hands and armour take one item only (except a hand takes a stack of a throwable); `Party.add_to_backpack` (portrait click) tops up matching stacks first. A potion in a quick slot uses one per use. **Inventory right-click on a stack splits rather than uses**; shift+right-click uses one (`event.shift_pressed`), as does a quick slot. The count is a 3x5 pixel digit in the icon's corner (`art/ui/digits.png` from `gen_ui.py`); `StackCount` sizes itself to its parent control by hand because anchors left it 0x0 inside an already-laid-out slot. A `Resource` is also a `RefCounted`: test `is Resource` first when telling an `ItemDef` from an `ItemStack`.

**Quick slots** (`quick_slot.gd`, two under each portrait in `party_hud.gd`; contents in `Party.Member.quick[2]` / `quick_cooldown[2]`, never on the shared `CharacterDef`): consumables (potions, scrolls) and throwables (`ItemDef.can_throw()`: dagger, darts) -- `Party.quick_accepts`; clicking or pressing the key of a throwable throws one (`Party._do_throw`, using the hero's action cooldown, not the slot cooldown). Same click-to-click cursor as the inventory, acting on press: left click with a held item puts it in (swap if full), left click empty-handed uses it on that hero (`Party.use_quick` -> `use_item`; spent only if it actually worked, then a `QUICK_COOLDOWN` 1.0 s per-slot cooldown drawn as a grey clock-wipe), right click lifts it onto the cursor. Hover shows the item name in the message line (`Hud.show_message(text, hold)` / `clear_message(only_if)`). Dead heroes' slots can't be used or filled, but right-click still lifts the item out so nothing is stranded. **Keys 1-8 are the quick slots** (hero 1 = 1,2; hero 2 = 3,4...; `player.gd`); the old 1-4 attack hotkeys are gone, attack by clicking a hand button. Not usable while the inventory is open. Art: `gen_ui.py` (`quickslot*.png`, 14x14).

**Combat** (rules come from the blueprint under *Design references*; this is only a summary). Real time, no turns. `combat_rules.gd` holds all the maths (hit % = 60 + 5 × (attack − defence), clamped 10–95; damage rolled from damage_min to damage_max; hero cooldown = max(0.8, 2.0 − 0.15 × speed)) and a seedable RNG (`CombatRules.seed_rng(n)` in tests). `CharacterDef` and `MonsterDef` share the stat fields, so `resolve_attack` works either way. The `Party` node (group `"party"`, heroes in slots 0–3, front row = 0–1) owns hero HP and cooldowns. `attack(slot)` hits the monster in `DungeonMap.occupied` in front of the player; `take_hit_from(monster)` picks a target by which side the monster is on. The party HUD reacts to `Party` signals and polls cooldowns, mana, buffs and hands each frame. Level complete and Game over share `end_screen.gd`, configured by `group_name`.

**Back row: hands, throwing, spells** (the blueprint's "Back row" section is the spec). Each HUD hand button acts with the item in *that* hand via `Party.act(slot, hand)`; `Party.action_for()` decides: melee weapon or empty hand -> swing if `can_melee` else "can't reach" (no cooldown); a throwable (`ItemDef.throw_damage_max > 0`) is thrown if `melee` is false (darts) or the hero can't melee (the back row throws a dagger, the front row stabs); a `FOCUS` (spellbook, holy symbol) opens `spell_menu.gd`. One action cooldown per hero covers swing, throw and cast. A throw flies up to `MISSILE_RANGE` 4 (walls/closed doors stop it), uses a normal hit roll, and the item lands on the monster's tile (hit or miss) or the last open tile; `dungeon.show_throw` is only the visual. **Floor tiles hold piles** (`dungeon_builder.items[cell].pile`, top last): `item_at`/`take_item` are the top stack, `place_item` merges into a matching top stack or goes on top, so dropping onto an item is allowed now. A hand may hold a stack only of a throwable (`inventory_slot.holds_stacks`). **Fireball** (the Mage's third spell, `data/spells/fireball.tres`; numbers agreed in the blueprint's Fireball section): 6 mana, 5-11 damage to the first monster ahead (never misses, up to `MISSILE_RANGE`), and `SpellDef.splash_radius` 1 / `splash_percent` 50: every other living monster on the 8 tiles around the target takes half of the same roll (rounded up, min 1; `Party._splash`), no second roll, the party is never hurt; the message adds "N more are caught in the blast.". A spell with no target, or too little mana, costs nothing. Its visuals are in **Spell lighting**.

**Spells** are `SpellDef` data (`data/spells/*.tres`, target AHEAD/HERO/PARTY) listed on the FOCUS item (`ItemDef.spells`); a hero casts only if `CharacterDef.magic` matches the item's `magic` and `max_mana > 0`. `Party.cast()` spends mana and the cooldown only when the spell takes effect; mana is a float regenerating 1 per `MANA_REGEN_TIME` 2.5 s, spells need whole points (`can_afford`). Shield/Bless are timed buffs in `Member.buffs`, counted by `effective_stats()`, which `take_hit_from` now uses for the defender too (recast refreshes). HUD: the mana bar row exists on every panel (invisible without mana) so rows line up; HERO spells enter target mode (next portrait click casts; a full-screen `catcher` under the panels, right-click or Esc cancels); the pop-up sits left of the whole grid. Starting kits come from `CharacterDef.start_hands`/`start_hand_counts`. `ItemDef.Type` and other enums are stored as numbers in `.tres`, so new values go at the end. Palette has no blue: mana and buff outlines use `torch_500`. In tests, `await process_frame` once isn't enough to see a node's `_process` result (the signal fires before nodes process): wait two frames.

**Character sheet** (`character_sheet.gd`, a child of the inventory screen, not a separate scene): a panel left of the inventory window showing portrait, class (a hero's `display_name` *is* their class), row, HP, mana (casters only), attack, defence, damage, swing time and equipped hands/armour, plus active buffs. Opened by clicking a hero's name on the party HUD (`show_screen(slot, true)`; ignored while choosing a spell target) or toggled by the name in the inventory header; portrait clicks open the inventory without it. It is a pure view, refreshed by `InventoryScreen.refresh()`, and follows the window's rect in `_process`. Stat values are `Party.effective_stats(m, -1, false)` -- gear only, buffs excluded -- compared with the `CharacterDef` base: better is `slime_300` with a `+n`, worse `rust_300` with `-n` (the palette has no red/green; the signed number covers colour-blindness). **Worn armour now adds its `defence_bonus` in `effective_stats`** (it used to be data only), so Leather Armour is +2 defence in combat as well as on the sheet. Don't name a method `_set` in a script: it collides with `Object._set`.

**Combat feel** (feedback only, no rules change): every effect and its numbers live in one resource, `data/combat_feel.tres` (script `combat_feel_config.gd`, grouped in the inspector), each with an `enabled` switch -- hit pause (a heavy blow or any kill freezes the game briefly via `Engine.time_scale`, restored by a timer that ignores time scale; `combat_feel.gd`, group `"combat_feel"`, fed by `Monster.take_hit` and `Party.hero_hit`), screen shake (camera `h_offset`/`v_offset`, scales with damage), monster telegraph (`monster.gd`: in the last `telegraph_seconds` of `attack_cooldown` it stretches, leans away and flashes, then lunges; the attack itself still fires on the unchanged schedule, and walking away or dying cancels it), miss messages (`Hud.show_message(text, hold, tone)` with tone `"miss"` adds the prefix and colour; `Party._say(text, tone)`), and portrait shake (`party_hud.gd`; the portrait lives in a plain `Control` frame because a container resets its children's positions). Read the config with `var feel_cfg: Resource = FeelConfigScript.get_config()` (a plain `load`), **never `preload` the .tres into a `const`**: Godot makes a const resource read-only, so runtime edits (tests, the remote inspector) silently do nothing, and a test can't even assign to it.

**Formation** (`Party.formation`, `swap_positions`, `set_formation`; HUD side in `party_hud.gd` "Formation drag"): a hero's *position* (`Member.slot`, 0-3, front row = 0-1) is separate from their identity (`Member.hero_index`, the index in `hero_defs`, never changes). `Party.members` is kept in position order and `Party.formation` is the hero_index per position (default `[0,1,2,3]`); that array is the party data a save/load stores, restored with `set_formation(order)` (rejects anything that isn't a permutation). A swap moves the whole `Member` (stats, hands, backpack, quick slots, mana, buffs, hp, dead or alive) and everything keyed by position -- `can_melee`, `action_for`, `_reachable_from` (who a monster hits), the HUD panels, quick-slot widgets (they are keyed by position and redraw on `quick_changed`) -- follows at once; `formation_changed` makes the HUD redraw each panel. **HUD panels are fixed positions**: closures in `_make_panel` must use the captured `pos`, never `m.slot` (the member standing there changes). The drag: press on a portrait or name, move 3 px, release over another panel; only when no item is on the cursor, no spell pop-up/target mode, and the game isn't paused. The drop target comes from the release *position* (`_panel_at`), not from Godot's control routing, which delivers a release to the control that got the press. `_drag_input` runs in `_input` before the GUI, so the release that ends a drag sets `drag_just_ended` (cleared next `_process`) and the portrait's `pressed` signal ignores it; names open the sheet on release for the same reason. Esc or right-click cancels a drag. Hand and quick slots never start one.

**Recovering thrown weapons** (all inside the click-to-pick-up system, no drag and drop): with an item on the cursor, clicking a hero's quick slot or hand button on the party panel puts it there directly (`Party.place_in_quick` / `place_in_hand`: place, top up a matching stack, or swap so the old item goes onto the cursor; a dead hero refuses; a cooling hand button stays enabled while the cursor holds something). A thrown piece on the floor remembers its home in `ItemStack.origin` (`{"hero": hero_index, "where": "hand"|"quick", "index"}` -- hero identity, so it survives formation swaps); picking it up (`Player._click_item`) calls `Party.return_to_origin`, which sends it back if that slot is empty or holds the same stack with room for all of it and the hero is alive, otherwise it comes onto the cursor. `merge_from` clears `origin` when two pieces with different homes merge, and the cursor never carries one. **Shift+click** on a floor item with an empty hand calls `Party.stow`: first free matching quick slot in party order (empty, or the same stackable item with room; living heroes only), then the first living hero's backpack with room; what fits nowhere stays on the floor. Messages: "Thief readies the dagger.", "Fighter stows the key.", "Thief takes back the darts."

**Spell lighting** (`spell_effects.gd`, node `SpellEffects` inside the dungeon SubViewport next to `Dungeon`, group `"spell_effects"`; every setting in `data/spell_effects.tres`, script `spell_effects_config.gd`, grouped in the inspector). Party calls it through the group and never holds it: `Party._fx(effect, cell)` runs `missile(from_cell, to_cell)` (Magic Missile and the scroll: a 7x7 palette-grey bolt sprite tinted light blue by `bolt_color` (HDR, so it blooms) with a moving blue `OmniLight3D` and a little trail, then an impact flash light that decays fast plus a one-shot spark burst) or `party_glow("heal"|"bless"|"shield")` (a warm or pale light pulse swelling and fading over `*_pulse_seconds`, and motes drifting up in front of the party). `fireball(from_cell, to_cell)` (a larger orange HDR orb, `fire_*` fields, with a light whose energy flutters each frame via `flickers` and an ember trail, then `explosion(cell)`: a large orange flash light (`blast_light_*`, range 18, fading over `blast_seconds` 0.5) that lights the whole area, a swelling orange orb, an ember spray, the `explosion` sound and a screen shake through `CombatFeel.shake_by(strength, seconds)`, which respects `screen_shake_enabled` in `combat_feel.tres`). `SpellDef.effect` names which one a spell plays (`missile`, `heal`, `bless`, `shield`; empty for none); a spell that does not take effect plays nothing. Effects are visual only and clean themselves up (`live` counts them). Colours above 1.0 are HDR. **Bloom and fog** are applied from the same resource by `SpellEffectsConfig.apply_environment(env, fog_on)` to the game's and the main menu's `WorldEnvironment`: glow uses `glow_hdr_threshold` 1.4 so only HDR things bloom and the torches do not blow out; the subtle **volumetric fog** (density 0.018) is switched by `Settings.fog` (Options: `FOG: ON/OFF`, saved under `[display]`, default on; set `fog_density` to 0 to remove it). The light blue is a real light colour: the 3D view's lighting is not palette-bound, only the bolt sprite pixels are. Read the config with `SpellEffectsConfig.get_config()` (plain load; never `preload` it into a const).

**Holy light** (Heal and Bless cast from a holy symbol; `Party.cast` emits `holy_cast(slot, hand, spell)` and calls `spell_effects.holy_pulse()`; settings in the "Holy light" and "Holy symbol on the party panel" groups of `data/spell_effects.tres`): a gold `OmniLight3D` swells outward from the party (range `holy_start_range` to `holy_light_range`) while the cracked wall's green crack dims (`Dungeon.dim_curse`, which tweens `emission_energy_multiplier` of the cracked-wall material; its emission map holds only the crack's pale-green core pixels, and **in Godot 4 an emission texture is ADDED to the emission colour, so the colour must be black** -- white made the whole wall glow). Only the cracked wall glows green by itself; mortar and rune glows do not exist yet. On the party panel `party_hud._on_holy_cast` lays `art/items/holy_symbol_glow.png` (three 32x32 frames from `gen_items.holy_symbol_glow`, drawn over the symbol's own hand icon with additive blending, gold only on some pixels so it stays worn) over the hand button as a `top_level` overlay (so a cooling hand's dimming does not dull it), pulsing `holy_hud_pulses` times over `holy_hud_seconds`, then fading over `holy_hud_fade`, with `holy_hud_motes` rising specks. A divine caster with no holy symbol in a hand gets "You need your holy symbol." (`Party.cast_refusal` / `cast`). **`Settings.reduce_flashing`** (Options: `REDUCE FLASHING`, saved under `[display]`) makes the holy light a weaker (`holy_reduced_scale`), steady glow that does not swell, and the panel glow one steady swell with no pulsing or motes; other effects (Fireball, Magic Missile) do not read it yet.

**Scroll of Resurrection** (`data/items/scroll_resurrection.tres`; rules in the combat blueprint's "Scroll of Resurrection" section; `ItemDef.revive_percent` 50 and `shaken_seconds` 20, so a scroll is data): `Party.revive(slot, def)` raises a hero at 0 HP with that share of max HP (rounded up, min 1) and no mana, keeping gear, quick slots and position (a living hero, or nobody fallen: "The scroll needs the fallen.", nothing spent); a divine caster (`CharacterDef.magic` DIVINE, the Cleric) returns with FULL HP but `Member.shaken_left` seconds of being shaken: no mana regeneration (`Party._process`), and `cast_refusal`/`cast` say "[Name] is too shaken to pray.", then "[Name]'s faith steadies." (death clears it; saved as `shaken` per hero, an older save has none). Three ways to read it: **on the cursor** (`party_hud._on_portrait`, or the inventory's portrait strip, `inventory_slot._click_portrait`, for a dead member; a living portrait keeps it), **from a quick slot** (`use_quick` emits `revive_requested`, the HUD enters `revive_pending` target mode, "Raise whom?", with the catcher up so Esc / right-click / `cancel_casting` cancels, and `revive_from_quick` spends it), and `use_item` (inventory right-click) only explains. The caller takes one scroll away when `used`. Feedback (HUD and `spell_effects.holy_pulse(scale)`, tunables in the "Resurrection" group of `data/spell_effects.tres`): the icon burns away in additive gold where it was read, a pixel-art gold column rises over the portrait (`_revive_column_texture`, wider, taller and brighter for a Cleric) with motes, the 3D gold pulse is stronger for a Cleric and dims curse glows, and a shaken Cleric's portrait carries a dimmed holy symbol; `Settings.reduce_flashing` makes the column dimmer and steadier with no motes. Floor 1 holds two (the secret closet behind the cracked wall and the locked closet). Do not run `import_pixellab.py` with stale files in `tools/art/inbox/`: it re-imports them over the current art.

**Pause menu** (`pause_menu.gd`, node `PauseMenu` in `main.tscn`, group `"pause_menu"`, canvas layer 19, built in code): Escape in play opens it and pauses; Escape or Resume closes it. Buttons: Resume, Save Game, Load Game (greyed with no save), Quit to Menu, Quit to Desktop. It saves through `SaveGame.save` directly (the F5/K refusal while paused lives in `SaveManager`, not `SaveGame`). Escape is used first by whatever is open: the inventory (`inventory_screen.gd` now marks it handled), the spell pop-up / target mode and formation drag (`party_hud.gd`); and the menu never opens when the tree is already paused (inventory, Level complete, Game over).

**Save and load** (`save_game.gd`, `save_manager.gd`; F5 or K saves, L loads (not F9: launched from the Godot editor with F5, the editor owns several F-keys and F9 froze the game after a load until pressed again), the main menu shows Continue when a save exists): one JSON slot at `user://savegame.json` (`SaveGame.path` is a var so tests use another file and never touch a real save). It stores the formation and every hero (hp, mana, hands, armour, backpack, quick slots, buffs; keyed by `hero_index`), the player cell/facing, floor piles (with `origin`), open/unlocked doors, lever states, live monsters (kind, cell, hp, attack timer) and the cursor item; items, spells and monsters are saved by resource path. Not saved: cooldowns, animations, floating text. **Loading reloads `main.tscn` and applies the file afterwards**: `SaveGame.load_game` stores `pending` and reloads, and `SaveManager._ready` applies it deferred, after everything is built; it relies on `Party.set_formation`, `Dungeon.restore_doors/restore_levers/set_pile/clear_monsters/spawn_monster` and `Player.restore`. JSON returns every number as a float, so convert with `int()` on the way in. A bad file is rejected before anything is changed (damaged, wrong version, wrong party, invalid formation); a missing item or monster definition is skipped. Saving is refused while paused (inventory, end screens); L works anywhere. Add new run state to `serialize` and `apply` together. In a SceneTree test script `self` is the tree, so pass `self` where code wants `get_tree()`.

**Audio** (`audio.gd`, one `Audio` node in `main.tscn` and one in `main_menu.tscn`, group `"audio"`; `settings.gd`; `tools/audio/gen_sounds.py`). Play an effect with `get_tree().call_group("audio", "play", "door_open")` (optional `volume_db`, `pitch`); scripts never hold the node, and a scene without one is simply silent. Sounds are procedurally synthesised mono 22050 Hz WAVs in `audio/sfx/` (variants `name_2.wav`, `name_3.wav`... are grouped under `name` and picked at random) plus a 24 s seamless ambient loop `audio/music/dungeon_drone.wav`; to use a real recording, drop a WAV of the same name in and stop the generator overwriting it. `audio.gd` has a 12-voice pool on the `SFX` bus, a `CUES` table (per-sound volume offset, pitch wobble, minimum gap so a held key can't machine-gun steps, bumps or clicks) and a `played` log that tests read. The loop is on the `Music` bus and fades in; its loop end is set in code from `get_length() * mix_rate` -- not `data.size()`, because Godot imports WAVs QOA-compressed. The editor lists both `x.wav` and `x.wav.import`, so the library loader dedupes. The node is `PROCESS_MODE_ALWAYS`, so clicks and the end-screen jingles sound while paused. `Settings.ensure_buses()` creates `Music` and `SFX` (sending to `Master`) at startup; volumes are `volume` (master 1.0), `music_volume` (0.7) and `sfx_volume` (1.0). Hooks live where the event happens: `player.gd` (step, bump, turn, locked/unlock, pickup/drop), `dungeon_builder.gd` (door open/close, lever, plate on and off), `party.gd` (swing, hit, whiff, hero hurt/die, throw, potion, scroll, spells, formation swap), `monster.gd` (attack, hurt, die), the inventory and quick slots (pickup/drop/click), `end_screen.gd` (plays its `group_name`: `level_complete` / `game_over`) and `save_manager.gd` (save, load). Spells name their sound in `SpellDef.sound`. A spell, potion or throw that does nothing makes no sound. Sounds have only been verified numerically (they were never auditioned), so expect to tune the levels in `CUES`.

**Rendering.** `project.godot` renders at 640x360 with `viewport` stretch and integer scaling (see "Display and pixel sizes" above). All pixel art must use nearest filtering and no mipmaps: materials set `TEXTURE_FILTER_NEAREST`, and each PNG's `.import` needs `mipmaps/generate=false`, `detect_3d/compress_to=0`, `compress/mode=0`. Godot rewrites `.import` defaults for new PNGs, so after importing run `build_all.py` (it patches them). The editor also rewrites `project.godot` and may strip comments.

## Art pipeline (`tools/art/`)

- **Follow `docs/art_style.md` for ALL art** (PixelLab prompts, procedural generators, hand-made): the game is a cursed, very dark, desaturated 1991-style dungeon with a few sparing curse accents (sickly pale green, bruised purple, dried blood), torchlight the only warm colour, a readability rule (clear silhouette, 1px `ink` outline, a hint of rim light or curse glow) and the exact target size of every asset. **Add its prompt suffix to every PixelLab request** (`dark cursed dungeon, gloomy, desaturated cold greys, deep near-black shadows, sickly pale green curse glow, decayed and rotten, 1991 pixel art, 1px dark outline, no anti-aliasing, limited palette, front view`), generate one asset first and get the style approved before making more, and route the result through `import_pixellab.py`.
- `palette.json` is the 32-colour "Cursed Dungeon" palette (the original 24 names with darker, colder values, plus `curse_*`, `bruise_*` and `blood_*`; UI scripts hard-code some of its colours as palette-named consts, both `Color("hex")` and `Color(r, g, b)  # Palette name` float literals: when a palette value changes, update both kinds (the float ones are found by the `# Palette name` comment; a missed set once made the empty quick slots the same colour as the party panel and invisible). Every generated image must use only those colours; `artio.save_png()` raises on any off-palette pixel. Use `PAL`/ramps from `palette.py`, not literal RGB.
- Helpers are flat modules (`from noise import ...`, no package): `noise` (seeded, tileable), `dither`, `outline`, `lighting` (light from the top-left), `artio` (`save_png`; `save_frames` for animation sets: frame PNGs + sheet + JSON; `patch_imports`).
- `build_all.py` runs every `gen_*.py` that defines `build()` returning the written paths. To add art, drop in a new `gen_<name>.py`.
- **`scale`**: `artio.save_png(img, path, scale=N)` enlarges the image N times (nearest) before the palette check and saving; a generator's `build(scale=2)` uses it for UI art only. Draw on the small logical grid, never at the enlarged size.
- **`import_pixellab.py`** replaces procedural art with PixelLab (or hand-made) PNGs: drop exports in `tools/art/inbox/`, run `python tools/art/import_pixellab.py` (`--dry-run` first; `--list` prints every expected asset and its size; `--dither`; `--scale`; `--restore KEY|all`). It snaps colours to `palette.json` (nearest, no dithering unless asked), resizes nearest-neighbour to the size of the art being replaced (**read from the files in `art/` at run time**, with the 2x UI scale for items, portraits and `ui/`), slices sheets into frames and renames everything to the existing file names, so no code changes. Originals go to `tools/art/_old/` the first time only (never overwritten by a later import); imported files are listed in `tools/art/imported.json`, and **`artio.save_png` skips those files, so `build_all.py` never undoes an import** (`--overwrite-imported` forces it). Frame-count mismatches, unmatched and ambiguous files are reported. A monster sheet with a different number of frames needs a layout file (`skeleton_sheet.layout.json`: `{"idle": 4, "attack": 3, "hurt": 2}`); the importer then also updates `data/monsters/<name>.tres` (`hframes`, `idle_frames`, `attack_frames`, `hurt_frames`). `python tools/art/test_import_pixellab.py` is its self-test (works on a temp copy). `tools/art/inbox/*` and `_old/` are git-ignored.
- **Animation frame counts are data, never code**: a monster's frames are `hframes` and the `idle_/attack_/hurt_frames` lists in its `MonsterDef` (plus `idle_fps`, `attack_fps`, `hurt_fps`); exactly two `hurt_frames` mean [hurt, flash] (alternating), any other count plays in order; a listed frame outside the sheet is clamped. The torch reads its frame count from its sheet (frames are 1:2, `torch_frames_from`). **Walking and standing**: a monster's `walk_frames` (extra frames at the end of the sheet, `walk_0`..; `walk_fps` 13, so four frames fill one 0.3 s step) loop while it steps between tiles (`monster._walking`, set in `_step`); an attack or hurt animation overrides it, and a monster with no walk frames keeps its idle frames while moving. **Feet on the floor**: `monster._foot_gaps()` counts, per frame, the transparent rows under the lowest opaque pixel (cached per sheet) and `_set_frame` shifts the sprite down by that, so any art stands on the floor however much empty space it has below (the first PixelLab sprites hovered 15 to 26 cm; a rendered test checks the lowest drawn pixel is within 2.5 px of the floor at 1, 2 and 3 tiles). The importer accepts `walk_N.png` (or `<monster>_walk_N.png`) for a monster that has none: it appends them to the sheet and sets `hframes` and `walk_frames` in the `.tres` without touching the other animations' hand-set frame lists. The lever is exactly two states (off, on). Portraits are three still images (living, hurt, dead), not an animation. **PixelLab portraits** are made at a **native 64x64, as an extreme close-up whose head fills the whole frame** (a bust left the face using only 50 to 90% of the frame and looked small in its panel; the panel has no room for a bigger picture) (finer than the procedural 32x32-logical ones, which are doubled; a 64x64 export is stored as is, the importer only doubles a 32x32 one) and only the living picture is generated: the importer derives the other two from it when it imports a `portraits/<hero>/portrait` (hurt: blended toward rust red; dead: greyed with a faint curse-green tint, `gen_portraits.cursed_dead_variant`, amount 0.62; `--no-variants` turns that off, and a hurt or dead picture supplied in the same import is used as given). The game has no character generator, races or Randomise button: the party is the four fixed heroes in `data/party/`. Sidecar `sprites/torch_sheet.json` / `lever_sheet.json` (from `gen_sprites.py`, `artio.save_sheet_info`) tell the importer a sprite sheet's frame size and whether its count may change.
- `art/` PNGs are **generated outputs**: edit the generators, or the next `build_all.py` overwrites your change. To use hand-made or PixelLab art instead, keep the same filenames and stop that generator from overwriting it.
- Frame/file names are the contract with the game (e.g. `art/monsters/skeleton/skeleton_sheet.png`, 7 frames of 48x64, referenced by `data/monsters/skeleton.tres`).
- `tools/.gdignore` keeps Godot from importing anything under `tools/`.

## Environment notes

- **PixelLab MCP** (`mcp__pixellab__*`, local scope) is live: an active subscription (checked with `get_balance`: 2000 generations this cycle, 0 used; the old "trial used up" note was stale).
